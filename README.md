# Hotel Social Report Agent

A small prototype for an agency that manages social media for hotels. It imports
social-media metrics, writes a monthly report for **one** hotel at a time, backs
every insight with the numbers it came from, and won't let anything leave the
system until a person approves it.

Built for the Noomoo AI Lab technical assessment. **All data is synthetic** - two
fictional hotels, generated by `scripts/generate_data.py`. No real brands, accounts
or credentials.

**Live demo:** https://hotel-social-report-agent.onrender.com (free hosting - the first load can take ~1 min while it wakes up; use "Reset demo data" at the bottom right to start clean)
**API docs:** https://hotel-social-report-agent.onrender.com/docs

---

## What it does

1. **Import** a CSV of post-level metrics (Instagram, Facebook, TikTok) for a client.
2. **Generate** a draft report: KPIs vs the previous month, breakdowns, and 5-8 insights.
3. **Show the evidence** behind every insight - values, sample sizes, the post ids used.
4. **Review**: edit the summary, drop weak insights, then **approve** or **reject** (with a note).
5. **Export** approved reports as Markdown, CSV or JSON. Drafts and rejected reports can't be exported.
6. Every step is written to an **audit trail**.

The two demo hotels are deliberately different so the reports come out different:

| Client | Story in the data |
|---|---|
| Atlas Riad Marrakech | reach and link clicks growing, Reels ~2.5x photos, TikTok under-used |
| Blue Coast Resort Agadir | engagement, reach and clicks all down vs September |

## Run it locally

Needs Python 3.11+.

```bash
python -m venv .venv
.venv\Scripts\activate          # macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
uvicorn app.main:app --reload
```

Open http://localhost:8000 (UI) or http://localhost:8000/docs (API).
The demo data loads automatically on first start; "Reset demo data" in the UI restores it.

**Optional - LLM wording:** copy `.env.example` to `.env` and set `ANTHROPIC_API_KEY`.
Without a key everything still works; insights use template wording.

Run the tests:

```bash
pytest
```

## How it works

```
CSV upload ──► validate (all-or-nothing) ──► SQLite (rows keyed by client_id)
                                                   │
                                   metrics.py  ◄───┘   pandas, deterministic KPIs
                                        │
                                   insights.py         rules -> findings + evidence
                                        │
                                   llm.py (optional)   Claude rewrites wording only
                                        │              number check on every sentence
                                        ▼
                                   draft report ──► human approve / reject ──► export
```

```
app/
  main.py       FastAPI routes + serves the UI
  db.py         SQLite, every query scoped by client_id
  importer.py   CSV validation
  metrics.py    KPI maths
  insights.py   rule-based findings with evidence
  llm.py        optional Claude wording + guard rails
  report.py     puts it together for one client
  export.py     Markdown / CSV / JSON
  static/       single-page UI (plain HTML/CSS/JS, no build step)
scripts/generate_data.py   synthetic data
tests/                     pytest
```

## Design decisions

**Numbers come from code, words from the model.** All KPIs are computed with pandas.
The LLM (Claude, `claude-opus-5-5` by default, configurable via `LLM_MODEL`) only
receives the findings that were already computed and is asked to phrase them for a
hotel manager. It never sees raw data and never does arithmetic.

**Every LLM sentence is checked.** Each number in the model's text must match a value
in that finding's evidence (at the precision it was written), and any post id must be
one of the finding's posts. If not, that sentence is dropped and the template text is
used instead. The UI says how many sentences were rejected. See `tests/test_llm_guard.py`.

**Weak insights don't get written.** A rule only fires with at least 3 posts behind it and a
meaningful gap (e.g. format ratio >= 1.3x, month-over-month change >= 5%). Sample sizes
are shown next to every claim.

**Client separation.** Client id always comes from the URL, never from the uploaded file.
Every DB function takes `client_id` and filters on it, so a report id from another client
returns 404 (same as "doesn't exist"). One LLM call = one client's findings. Tests in
`tests/test_isolation.py` cover reading, approving and importing across clients.

**Human in the loop.** Reports start as `draft`. Only a draft can be approved or rejected,
rejecting requires a note, and export is blocked (HTTP 409) unless the report is approved.
Reviewer edits (summary changes, removed insights) are recorded in the audit log.

**Engagement rate** = (likes + comments + shares + saves) / reach, reach-weighted across
posts (not an average of per-post rates, which over-weights tiny posts).

## API (short version)

| Method | Path | |
|---|---|---|
| GET | `/api/clients` | list clients |
| GET | `/api/clients/{id}/overview` | KPIs + breakdowns for the latest month |
| POST | `/api/clients/{id}/import` | upload CSV (`file`) |
| POST | `/api/clients/{id}/reports` | generate a draft |
| GET | `/api/clients/{id}/reports/{rid}` | report + audit trail |
| POST | `/api/clients/{id}/reports/{rid}/approve` | `{reviewer, summary?, excluded_insights?, note?}` |
| POST | `/api/clients/{id}/reports/{rid}/reject` | `{reviewer, note}` |
| GET | `/api/clients/{id}/reports/{rid}/export?fmt=md\|csv\|json` | approved only |

Full interactive docs at `/docs`.

## Deploy

`render.yaml` deploys the app as a free Render web service (connect the GitHub repo,
Render picks up the blueprint). Set `ANTHROPIC_API_KEY` in the Render dashboard if you
want LLM wording; `LLM_MAX_REPORTS_PER_HOUR` caps usage on the public demo. The free
tier's disk is temporary, so the app re-seeds the demo data on every start.

## Limitations / what I'd do next

- No login - in a real version reviewers would authenticate and clients would only see their own reports.
- SQLite with app-level scoping; for production I'd use Postgres with row-level security as a second line of defence.
- CSV import only; next step would be connectors for the Meta Graph API and TikTok API.
- PDF export and branded templates per hotel.
- Month-over-month only; seasonality and paid vs organic split would make the insights sharper.
